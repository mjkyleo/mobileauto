# 手机自动化任务方案（汽水音乐实战总结）

> 本文把汽水音乐「领时长」任务从踩坑到成熟的全过程整理成方法论，用于指导创建新 App / 新任务的自动化。
> 核心代码：`src/mobileauto/flow_engine.py`（通用引擎）、`src/mobileauto/qishui_runner.py`（成熟参考实现）、
> `src/mobileauto/task_template.py`（新任务模板）、`src/mobileauto/flow_probe.py`（探测工具）。

---

## 一、完整任务流程（汽水音乐领时长，实测状态机）

```
启动 App
   ↓
开屏广告（识别"跳过 N" → 秒点跳过）
   ↓
HOME 首页（底部导航，点"福利"）
   ↓
WELFARE 福利中心（点"领时长" / "再看1次"）
   ↓
广告页 AD（点静音；识别右上角 ×）
   ↓
COUNTDOWN 倒计时（"XX秒后可领取奖励" → 只等待，不点击）
   ├─→ 可能进直播间 → LIVE → 立刻点直播 × 秒退 → 回倒计时
   └─→ REWARD 奖励弹窗（点"领取奖励"）
           ↓
       SUCCESS 领取成功尾页（点 × 或返回键退出）
           ↓
       CONTINUE 续看弹窗（"再看20秒得" → 点"继续观看"）或回到 WELFARE 下一轮
           ↓
       DONE 结束（"明日再来" 灰色 + "畅听权益截止 12/24 24:00" → 输出信息并停止）
```

### 状态与动作对照表

| 状态 | 识别关键词（OCR） | 动作 | 优先级 |
| --- | --- | --- | --- |
| DONE | 明日再来 / 畅听权益截止 / 已领完 | 提取截止日期，停止 | 最高 |
| SPLASH | 跳过 + 开通SVIP/汽水音乐 | 点"跳过" | 高 |
| CONTINUE | 继续观看 / 再看XX秒得 | 点"继续观看" | 高 |
| REWARD | 领取奖励 / 立即领取（排除"秒后"） | 点按钮 | 高 |
| COUNTDOWN | 秒后可领取 / 秒可领取 | 只等待 + 静音 | 中 |
| LIVE | 说点什么 / 本场点赞 / 更多直播 | 点直播 × (1350,250) | 中 |
| LANDING | 点击进入直播间（排除"说点什么"） | 点顶部 × | 中 |
| SUCCESS | 领取成功 / 恭喜获得奖励 | 点 × 或返回键 | 中 |
| WELFARE | 领时长 / 福利中心 / 免费听时长 | 点"领时长" | 低 |
| HOME | 福利（排除福利中心）+ 我的/音乐 | 点"福利" | 低 |
| AD | 广告 / 反馈 / 立即下载 | 静音 | 最低 |

## 二、踩过的坑（血泪史，逐条对应修复）

### 1. 用 UI 层级找按钮 → 完全失效
- **现象**：`dump_hierarchy` 找不到"跳过"，只能每秒盲点右上角，12 次重试，反应极慢。
- **根因**：App 是 Canvas 自绘，UI 层级里文字基本为空。
- **教训**：**自绘 App 一律走屏幕 OCR**，不要依赖 UI 层级 / resource-id。

### 2. 固定坐标盲点 → 点到别的 App
- **现象**：手机停在微信朋友圈，脚本按 (720,1664) 点"领取奖励"，点到了朋友圈。
- **根因**：没有校验当前 App / 页面是否是目标页面。
- **教训**：**点击前必须确认页面特征**；加 App 前台校验；OCR 没识别到目标文字时宁可不点。

### 3. 倒计时被误当成按钮 → 无限死循环
- **现象**："17秒后可领取奖励"里含"领取奖励"，被当成按钮狂点，卡住。
- **根因**：关键词"包含匹配"没排除倒计时文案。
- **教训**：**倒计时词永不当按钮**；`exclude=["秒后","秒可"]`；倒计时状态只等待。

### 4. 直播广告进直播间出不来
- **现象**：直播广告倒计时结束自动进直播间，没有普通 ×，卡死。
- **根因**：直播页和广告页的关闭按钮位置不同（直播 × 在 1350,250，普通 × 在 1330,85）。
- **教训**：**识别出直播专属元素（说点什么/本场点赞）→ 用直播专用 × 秒退**，绝不点"进入直播间"。

### 5. 前景弹窗被背景误判
- **现象**：奖励弹窗叠在直播背景上，OCR 同时有"领取奖励"和"直播中"，被判成直播，一直点 ×。
- **根因**：状态优先级错误，背景特征抢了前景弹窗。
- **教训**：**状态判定严格按优先级**：结束态 > 前景弹窗 > 倒计时 > 页面；前景弹窗永远优先。

### 6. 领取成功提示条反复点
- **现象**："领取成功"是状态提示不是按钮，脚本反复点它。
- **教训**：**区分"状态文字"和"可点按钮"**；带 × 就点 ×，否则返回键退出。

### 7. "继续观看"续看弹窗没处理
- **现象**："再看20秒得 / 继续观看"弹窗没识别，卡住。
- **教训**：**探测要看全所有页面**，漏掉一种状态就卡一次；每发现新页面就补一个状态。

### 8. 结束态没识别 → 点灰色按钮
- **现象**：领完当月，"领时长"变灰色"明日再来"，脚本还去点，卡住。
- **根因**：没有结束态检测。
- **教训**：**必须有明确结束条件**；结束态优先级最高；结束时要输出关键信息（畅听权益截止）。

### 9. 点完不验证 → 点了没反应也不知道
- **现象**：灰色按钮点了没效果，脚本继续往下走，流程错乱。
- **教训**：**每个动作后验证页面是否真的变化**；没变就重试一次/换策略；统计成功失败数。

### 10. 日志刷屏、格式混乱
- **现象**：每帧打印整屏 OCR，窗口滚得看不清做了什么。
- **教训**：**分层日志**：页面切换（带 1 个触发词）/ 动作（缩进 2 格）/ 验证结果（缩进 5 格 [OK]/[FAIL]）；每轮分隔线；起止框。

### 11. 连接回退
- **现象**：改 `connect_device` 时删掉了 `u2.connect()` 空地址自动检测，之前能连变成连不上。
- **教训**：**改连接逻辑要保留原有可用路径**；自动检测兜底不能删。

### 12. 编码崩溃
- **现象**：日志里用 `✔`/`⚠` 符号，Windows GBK 控制台直接崩。
- **教训**：控制台输出用纯 ASCII 标记 `[OK]`/`[FAIL]`；脚本开头 reconfigure stdout/stderr 为 UTF-8。

## 三、可复用的核心思想（创建任何任务都适用）

1. **先探测，后编码**：新任务第一步永远是跑 `flow_probe.py`，把每页截图+OCR+状态存到 `runtime/flow_probe/state_log.jsonl`，看清全流程再写状态机。**不要凭猜测写点击**。
2. **OCR 驱动**：自绘 App 靠 OCR，文字坐标即点击坐标。
3. **状态机优于脚本式顺序**：每帧判定状态 → 按状态动作 → 循环；比 `while True` 里一堆 if 更稳、更易扩展。
4. **状态判定按优先级**：用有序规则列表，第一个命中胜出；结束态和前景弹窗最优先；倒计时排除。
5. **动作必验证**：`verify_action()` 检查页面是否变化，失败重试/换策略；统计成败。
6. **防卡死三件套**：同一状态超时计数 + 返回键兜底 + 明确结束态。
7. **一次性动作标记**：静音等只做一次（flag），避免每帧重复点。
8. **点击去重**：`TAP_GAP` 最小间隔，避免连点。
9. **分层日志**：少而精，关键节点可见，可回溯。
10. **坐标用实测**：从采集/OCR 结果取真实坐标，不猜比例；比例坐标只作兜底。

## 四、工作台里的可选能力（核心能力已抽离）

上述能力在 PC 工作台里**全部是可选开关，不是强制流程**。每个任务的 JSON 里都有 `capabilities` 块，前端「任务列表 → 编辑」区有对应勾选框，勾选即启用、取消即关闭。不同场景（循环领时长 / 每日打卡 / 一次性任务）可按需组合。

### 能力清单

| 能力键 | 名称 | 作用 | 适用场景 |
| --- | --- | --- | --- |
| `ocr` | OCR识别 | 从屏幕识别文字与坐标驱动流程 | 自绘 App 必开；控件化 App 可关 |
| `action_verify` | 动作验证 | 点击后检查页面是否真变化，失败重试 | 需要确认每一步生效的任务 |
| `anti_stuck` | 防卡死 | 同一状态多次无变化→返回键兜底 | 广告/弹窗多的场景 |
| `dedupe` | 点击去重 | 最小间隔内不重复点同一位置 | 所有场景（防连点） |
| `structured_log` | 分层日志 | 页面/动作/验证三级日志+轮次框 | 需要看实时过程时 |
| `end_detect` | 结束检测 | 识别结束态并停止任务 | 有明确完成条件的任务 |
| `auto_start` | 自动启动 | 启动时拉起目标 App | 需从桌面自动进入的任务 |
| `entitlement` | 结束信息 | 结束时提取关键信息（如截止日期） | 需输出结果的通知类任务 |

### 两种执行引擎（按场景选）

1. **步骤流程（旧版，兼容）**：任务 JSON 不填 `engine`，走 `app_task.py` + 规则包 `flow.steps`。汽水音乐领时长任务用这条，流程固定、成熟稳定。
2. **配置驱动（新场景推荐）**：任务 JSON 填 `"engine": "configured"`，用 `configured_flow.py` + `flow_engine.py`，只需在 JSON 里写 `states`（状态判定+动作）即可，**不用写 Python 代码**。示例见 `tasks/示例-每日打卡.json`（默认生成的 `daily_checkin`）。

### 配置示例（每日打卡场景）

```json
{
  "key": "daily_checkin",
  "name": "示例-每日打卡",
  "app": "com.example.app",
  "engine": "configured",
  "max_loops": 1,
  "capabilities": {
    "ocr": true, "action_verify": true, "anti_stuck": false,
    "dedupe": true, "structured_log": true, "end_detect": true,
    "auto_start": true, "entitlement": false
  },
  "states": [
    {"name": "DONE", "match": ["已完成", "明日再来"], "action": "finish"},
    {"name": "REWARD", "match": ["领取奖励"], "exclude": ["秒后"], "action": "click_match", "count": true},
    {"name": "MAIN", "match": ["去领取", "打卡"], "action": "click_match"},
    {"name": "HOME", "match": ["首页"], "action": "wait"}
  ],
  "stuck_states": ["REWARD"],
  "finish_info_keywords": ["已完成"]
}
```

动作类型：`click_match`（点命中文字）/ `click_ratio`（点比例坐标）/ `back` / `wait` / `finish` / `close_ad` / `mute_once`。

### 向后兼容

- 旧任务 JSON 没有 `capabilities` 字段时，启动时自动补齐为全开，不覆盖已有编辑。
- 旧规则包没有 `flow` 时也会自动补齐。
- 原有汽水音乐任务、bat 启动器、工作台功能均不受影响。

## 五、创建新任务的标准流程

### 第 1 步：探测目标 App
复制 `flow_probe.py`，改 `APP_PACKAGE` 和关键词，跑一遍完整流程：
```bash
python -m mobileauto.flow_probe
```
查看 `runtime/flow_probe/state_log.jsonl` 和截图，列出所有页面状态。

### 第 2 步：写状态判定
在 `task_template.py` 的 `STATES` 里，按优先级列出每个状态的关键词；
注意排除词（倒计时、背景误判）。

### 第 3 步：写动作处理
在 `handle()` 里为每个状态写动作，用引擎提供的方法：
- `engine.tap_item(item, label)` 点 OCR 命中的文字
- `engine.tap_ratio(rx, ry, label)` 点实测比例坐标
- `engine.verify_action(状态, 动作名)` 验证是否成功
- `engine.press_back()` 返回键兜底
- `engine.finish(标题, 信息...)` 标记结束

### 第 4 步：配置并运行
改 `CONFIG`（名称/包名/轮数），设 `engine.stuck_states`（易卡住的状态），运行：
```bash
python -m mobileauto.my_task
```

### 第 5 步：迭代
看日志里 `[FAIL]` 和状态卡住的地方，回到第 1 步补充探测和关键词。
